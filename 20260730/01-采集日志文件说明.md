# 采集日志文件说明

YouTube 加密视频自动化采集系统在一次采集会话中生成三种日志文件，分别记录任务编排、播放器状态和系统底层的不同层面信息。三者相互配合，支撑从原始采集到后续分析的全流程。

## 文件命名规则

三种日志共享同一前缀，包含采集会话的关键元数据：

```
YouTube-EncryptedVideo-Android-{session_id}-{network_type}-{network_detail}-{timestamp}-{device}-{video_id}-{resolution_mode}-{app}-{region}.{ext}
```

以本次会话为例：

```
YouTube-EncryptedVideo-Android-3a9d9d25a6424928937939c36842a1df-Wifi-Open-20260613_234015-yb01-ENt4uip1MJ8-auto-YouTube-HongKong
```

各字段含义：

| 字段 | 示例值 | 含义 |
|------|--------|------|
| session_id | `3a9d9d25a6424928937939c36842a1df` | 采集会话唯一标识（UUID） |
| network_type | `Wifi` | 网络类型 |
| network_detail | `Open` | 网络细节（如 Open 表示开放网络） |
| timestamp | `20260613_234015` | 采集启动时间（UTC+8） |
| device | `yb01` | 采集设备编号 |
| video_id | `ENt4uip1MJ8` | YouTube 视频 ID |
| resolution_mode | `auto` | 分辨率模式（auto 为自适应码率） |
| app | `YouTube` | 采集应用 |
| region | `HongKong` | 节点区域 |

## 1. operate.log — 任务编排日志

**文件后缀**：`.operate.log`

**定位**：自动化采集框架的完整操作执行记录，记录"做了什么操作、什么时候做的"。

### 内容结构

每行一条日志，格式为：

```
[时间戳 UTC Unix.微秒 级别] 模块(行号) - 消息内容
```

### 记录的操作阶段

一次完整的采集会话按顺序经历以下阶段：

1. **初始化**：计算手机与服务器的时间偏移（`phone_to_server_time_offset`），用于后续时间对齐。
2. **ADB 日志捕获启动**：通过 `adb logcat` 开始采集系统日志，同时指定输出文件路径。
3. **应用清理**：强制停止所有应用，清除 YouTube 缓存，确保采集环境干净。
4. **流量捕获启动**：初始化 PCAP 抓包和 metadata 记录。
5. **屏幕录制启动**：通过 scrcpy 启动屏幕录制（指定设备序列号、码率、音频编码等参数）。
6. **视频搜索与播放**：
   - 搜索目标视频（按 video_id）。
   - 判断分辨率模式：若为 `auto` 则无需手动暂停和切换码率。
   - 记录播放前视频进度和总时长。
   - 点击全屏播放。
7. **观看期**：等待指定时长（如 300 秒），后台线程每 2 秒调用 `get_debug_info` 采集播放器调试信息，并记录每次调用的耗时。
8. **结束清理**：
   - 停止观看。
   - 后台日志写入线程安全退出。
   - 停止屏幕录制。
   - 停止 ADB 日志捕获。
   - 停止流量捕获。

### 关键字段

| 字段 | 说明 |
|------|------|
| `phone_to_server_time_offset` | 手机时钟与服务器时钟的偏移量（毫秒），用于跨设备时间对齐 |
| `pcap file` / `metadata file` | PCAP 和 metadata 文件的存储路径 |
| `get_debug_info 执行耗时` | 每次采集播放器调试信息的耗时（通常 1.2~2.8 秒），可用于评估采集开销 |
| `播放前视频进度` / `视频总时长` / `播放结束视频进度` | 视频播放起止位置，用于确认采集覆盖范围 |

### 典型用途

- 验证采集流程是否完整执行（无跳过阶段）。
- 排查采集异常（如 scrcpy 启动失败、缓存清除失败）。
- 时间对齐：将 PCAP、debug_info 和 adb_log 的时间线关联。

## 2. debug_info.txt — 播放器调试信息

**文件后缀**：`.txt`（文件名含 `debug_info`）

**定位**：YouTube 播放器内置的 "Stats for Nerds" 调试面板的周期性快照，记录"视频播放的实时状态"。

### 内容结构

每条约 4 秒采集一次，格式为多行键值对，条目之间以空行分隔：

```
Time: 2026-06-13 23:41:14
Device: Xiaomi 25053RT47C 16
sCPN: KJAX JXHE BNS5 WQG3 0N60  [plat]
Video ID: ENt4uip1MJ8  [vod]
Video format: 721 av01 1920x1080@24
Audio format: 251:... opus
Volume/Normalized: 66%/66%(P:-16.5LK/T: -14.0LK/G: 0.0LK)
Bandwidth:  0.00 kbps
Readahead:  13.5 s
Viewport: 2275x1280xfalse
Dropped frames: 1 / 555
Mystery Text: G
```

### 字段详解

| 字段 | 说明 |
|------|------|
| **Time** | 采集时刻（设备本地时间） |
| **Device** | 设备型号与 Android 版本 |
| **sCPN** | 播放会话唯一标识（Content Playback Notification），`[plat]` 表示平台播放器 |
| **Video ID** | YouTube 视频 ID，`[vod]` 表示点播视频 |
| **Video format** | 视频流信息：`ITAG 编码 分辨率@帧率`。ITAG 是 YouTube 内部的格式编号 |
| **Audio format** | 音频流信息：`ITAG:Base64编码的元数据 编码` |
| **Volume/Normalized** | 当前音量/标准化音量，括号内为响度参数（P: 峰值、T: 目标、G: 增益） |
| **Bandwidth** | 当前网络带宽估计值，初始为 0 表示缓冲阶段，稳定后反映实际吞吐 |
| **Readahead** | 预读缓冲时长（秒），越大表示缓冲越充足 |
| **Viewport** | 视口尺寸 `宽x高x是否旋转` |
| **Dropped frames** | 丢帧数 / 已渲染总帧数 |
| **Mystery Text** | YouTube 内部调试标记 |

### ITAG 参考值

本次会话中出现的 ITAG：

- **721**：AV1 编码，1920x1080，24fps（高清视频流）
- **251**：Opus 编码，音频流

### 典型用途

- **ABR（自适应码率）分析**：追踪 Bandwidth 和 Video format 的时序变化，研究码率切换策略。
- **缓冲行为分析**：Readahead 的变化反映缓冲区的充盈与消耗，结合 Bandwidth 可分析卡顿与重缓冲事件。
- **播放质量评估**：Dropped frames 反映播放流畅度。
- **与 PCAP 交叉验证**：将 debug_info 的时间戳与 PCAP 中 QUIC 流量对齐，可将网络行为与播放器状态关联。

## 3. adb_log.txt — Android 系统日志

**文件后缀**：`-adb_log.txt`

**定位**：通过 `adb logcat` 采集的 Android 设备全量系统日志，记录"设备层发生了什么"。

### 内容结构

标准 logcat 格式：

```
MM-DD HH:MM:SS.mmm L/Tag (PID): message
```

其中 `L` 为日志级别（`V`=Verbose, `D`=Debug, `I`=Info, `W`=Warn, `E`=Error, `F`=Fatal）。

### 主要内容类别

| 类别 | 关键标签 | 说明 |
|------|----------|------|
| **应用崩溃** | `F/libc`, `F/DEBUG` | 进程崩溃堆栈，含信号类型、寄存器、调用栈回溯 |
| **UI 自动化** | `I/System.out` | poco-uiautomation-framework 的节点选择与属性查询，用于自动化操控 YouTube 界面 |
| **视频编解码** | `D/CCodecConfig`, `W/QC2Comp` | 编解码器配置与状态，如 AV1 解码器参数 |
| **图形显示** | `W/Layer`, `I/SDM` | SurfaceFlinger 缓冲区状态、Concurrent Writeback (CWB) 配置 |
| **内存管理** | `D/JavaheapMonitor`, `I/DMABUFHEAPS` | Java 堆使用量、DMA-BUF 堆分配 |
| **系统服务** | 各系统进程 | 传感器、输入事件、包管理等系统级事件 |

### 典型用途

- 排查 scrcpy 崩溃（`com.genymobile.scrcpy.CleanUp` / `com.genymobile.scrcpy.Server` 的 ClassNotFoundException）。
- 分析 UI 自动化操作的执行细节（poco 框架的节点选择器查询了哪些界面元素）。
- 调查视频编解码异常（解码器跳帧、缓冲区延迟）。
- 底层系统问题的根因分析。

### 注意事项

- 文件体量大（单次采集可达数十 MB、数十万行），直接全文阅读不现实，建议结合 `grep` 按标签或 PID 过滤。
- 日志包含采集前设备的累积记录（crash 堆栈可能来自更早时间），需注意时间戳筛选。

## 三种日志的协作关系

```
operate.log          debug_info.txt       adb_log.txt
(任务编排层)          (应用状态层)          (系统底层)
    |                     |                    |
    |-- 操作时间线 --------|                    |
    |   (何时做什么)       |-- 播放器状态时序 ---|
    |                     |   (码率/缓冲/帧)   |-- 系统事件
    |                     |                    |   (崩溃/编解码/内存)
    +------ 时间对齐 ------+------ 时间对齐 ----+
                (phone_to_server_time_offset + 本地时间戳)
```

- **时间对齐**是三者协作的核心：operate.log 记录了 `phone_to_server_time_offset`，可据此将设备本地时间（debug_info、adb_log）与服务器时间（PCAP 抓包时间）对齐。
- **operate.log** 提供"做了什么"的全局视图，是理解采集上下文的首选入口。
- **debug_info.txt** 提供播放器的精细状态时序，是 ABR 与缓冲分析的主要数据源。
- **adb_log.txt** 提供系统级深挖能力，是排障和底层行为分析的最终参考。

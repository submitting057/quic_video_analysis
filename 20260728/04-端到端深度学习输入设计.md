# YouTube 视频 ID 识别的端到端深度学习输入

这里的“端到端”建议定义为：从被动可观察的 UDP Datagram 元数据直接学习 `video_id` 或 embedding，而不是将 PCAP 文件头、IP、端口、CID 和加密 payload 原样输入网络。

两位独立高级 agent 分别从包级信息保留和多尺度鲁棒性出发进行头脑风暴，形成以下共识：

- 严格无密钥旁路场景应以一个 UDP Datagram 为基本事件。
- 不应假设一个 PCAP Record 等于一个 QUIC Packet，也不应假设能够准确分离 HTTP/3 Stream。
- 包长、方向和时间是第一版最稳定的输入。
- 多连接关系可以通过会话内匿名路径编号表达，不能输入真实 IP、端口或 CID。
- 包级事件序列信息更完整；时间 Bin 输入通常对现实网络变化更鲁棒。

## 一个训练样本是什么

```text
一个样本 = 一次独立播放会话在固定观察时间内的全部目标 UDP Datagram
一个标签 = 该播放会话的 video_id
```

不是一个包对应一个视频标签，也不是一个五元组必然对应一个完整视频会话。

结构化样本示例：

```json
{
  "session_id": "session_000123",
  "video_id": "dQw4w9WgXcQ",
  "observation_seconds": 30,
  "datagrams": [
    {
      "relative_time_ms": 0.0,
      "direction": -1,
      "udp_payload_length": 1200,
      "path_id": 0
    },
    {
      "relative_time_ms": 18.0,
      "direction": 1,
      "udp_payload_length": 1192,
      "path_id": 0
    }
  ]
}
```

## 方案 A：最小 Datagram 事件序列

### 基础两维输入

最简单的序列输入：

```text
[
  signed_udp_payload_length,
  log_inter_arrival_time
]
```

方向约定可以任意，但必须一致。本文采用：

```text
服务器 → 客户端：正
客户端 → 服务器：负
```

示例：

| 时间/s | 方向 | UDP Payload | IAT/ms | 事件输入 |
| ---: | --- | ---: | ---: | --- |
| 0.0000 | 客户端→服务器 | 1200 | 0 | `[-1200, 0.0]` |
| 0.0180 | 服务器→客户端 | 1192 | 18.0 | `[1192, 18.0]` |
| 0.0192 | 服务器→客户端 | 1200 | 1.2 | `[1200, 1.2]` |
| 0.0200 | 服务器→客户端 | 350 | 0.8 | `[350, 0.8]` |
| 0.0440 | 客户端→服务器 | 42 | 24.0 | `[-42, 24.0]` |

### 推荐四维输入

为了处理多个路径和全局交错，推荐扩展为：

```text
[
  signed_udp_payload_length,
  log_global_iat,
  log_path_iat,
  relative_time
]
```

含义：

- `global_iat`：与整个播放会话中前一个 Datagram 的时间间隔。
- `path_iat`：与同一匿名路径中前一个 Datagram 的时间间隔。
- `relative_time`：相对观察起点的位置。

归一化：

```text
length_feature = signed_udp_payload_length / 1500
global_iat     = zscore_train(log1p(clip(global_iat_ms, 0, 10000)))
path_iat       = zscore_train(log1p(clip(path_iat_ms, 0, 10000)))
relative_time  = t_rel / observation_duration
```

不能按每个会话单独缩放包长，因为绝对流量规模可能正是视频指纹的一部分。所有均值和标准差只能从训练集计算。

### 输入张量

以 30 秒、最多 8192 个 Datagram 为例：

```text
X_event: [B, 8192, 4]
path_id: [B, 8192]
mask:    [B, 8192]
y:       [B]
```

其中：

```text
B        = batch size
8192     = 最大 Datagram 数
4        = 连续特征数
path_id  = 会话内匿名路径编号
mask     = 真实事件或 Padding
y        = video_id 对应的类别或训练标签
```

不足 8192 个事件时补零并使用 Mask；超过上限时截断。更稳妥的做法是根据训练集 30 秒事件数量的高分位数确定 `L`，而不是先验固定 8192。

### 匿名路径编号

不输入真实五元组、IP、端口或 CID，而是在每个会话内分配匿名编号：

```text
首次出现的路径 A → 0
首次出现的路径 B → 1
首次出现的路径 C → 2
```

`path_id` 仅表达“哪些事件属于同一可观察路径”，不代表已恢复真实 QUIC 逻辑连接。

### 适用模型

- 1D CNN 或 TCN 学习局部连续大包和上下行交互。
- 局部 Transformer 学习中长程下载节奏。
- CNN/TCN 先下采样，再交给 Transformer，可降低长序列成本。

优点是信息保留完整；缺点是序列长，容易受到 RTT、拥塞、丢包、MTU 和捕获位置影响。

## 方案 B：多尺度时间 Bin

多尺度方案使用确定性时间聚合，牺牲 Bin 内顺序以提高固定长度和网络鲁棒性。

将 30 秒观察窗按 20 ms 划分：

```text
30 秒 / 20 ms = 1500 个 Bin
```

每个路径、每个 Bin 统计：

```text
[
  downstream_bytes,
  upstream_bytes,
  downstream_small_count,
  upstream_small_count,
  downstream_medium_count,
  upstream_medium_count,
  downstream_large_count,
  upstream_large_count
]
```

示例大小分组：

```text
small  ≤ 160 B
medium = 161～1000 B
large  > 1000 B
```

一个 20 ms Bin 中出现下行 `1200、1200、1180、350` 字节和一个上行 `42` 字节 Datagram 时：

```text
[
  3930,  // 下行总字节
  42,    // 上行总字节
  0,     // 下行小包数
  1,     // 上行小包数
  1,     // 下行中包数
  0,     // 上行中包数
  3,     // 下行大包数
  0      // 上行大包数
]
```

保留流量最大的 `K=4` 条候选路径，其余路径合并为 `other`。对于 30 秒观察窗：

```text
X20:   [B, 5, 1500, 8]
X100:  [B, 5,  300, 8]
X500:  [B, 5,   60, 8]
Mpath: [B, 5]
```

`X100` 和 `X500` 可以由 `X20` 确定性求和池化得到。

三个尺度分别侧重：

```text
20 ms  → 局部包团和请求响应
100 ms → 下载 Burst 形状
500 ms → 较长下载节奏和 ABR 周期
```

不同路径应使用共享编码器，然后通过 Set Attention 或无序池化融合。不能让模型认为“第一个路径”始终具有固定业务语义。

优点：

- 固定输入长度。
- 不会因为高速会话包数更多而过早截断。
- 对轻微重排和起点抖动相对稳定。
- 更容易学习较长的下载周期。

缺点：

- 丢失 Bin 内事件顺序。
- 效果依赖时间和包长分箱粒度。
- 属于确定性弱预处理后的端到端，而不是 raw-PCAP-to-label。

## 方案 C：双视图输入

性能上限模型可以同时输入：

```text
事件分支：
X_event [B, L, 4]
path_id [B, L]
mask    [B, L]

聚合分支：
X20  [B, 5, 1500, 8]
X100 [B, 5,  300, 8]
X500 [B, 5,   60, 8]
```

```text
事件序列 → TCN / 局部 Transformer ─┐
                                    ├→ 融合 → Session Embedding
多尺度 Bin → CNN / TCN ─────────────┘
```

事件分支保留细粒度交互，多尺度分支学习稳定的长程下载结构。

实验中应先分别验证两个分支，再验证融合，避免无法判断性能提升来自哪种表示。

## 方案 D：Burst 或 Packet-Burst 分层输入

可解释的 Burst 输入：

```text
X_burst: [B, M, 7]

每个 Burst：
[
  direction,
  log_bytes,
  log_packet_count,
  duration,
  preceding_gap,
  large_packet_ratio,
  small_packet_ratio
]
```

纯 Burst 特征依赖人工空闲阈值，属于深度模型匹配人工表示。更接近端到端的方式是：

```text
固定规则只确定 Burst 边界
→ Packet Encoder 学习每个 Burst 的 embedding
→ Session Transformer 学习 Burst 序列
```

固定阈值会受到 RTT、吞吐量、ABR 和丢包影响，因此 Burst 方案适合作为可解释基线，不建议作为唯一主输入。

## 会话起点

训练时最好通过浏览器自动化或实验日志记录真实点击播放时间：

```text
t0 = 点击播放或确认媒体开始的时间
T  = 10 / 30 / 60 秒观察窗
```

不能简单使用 QUIC 连接建立时间，因为浏览器可能复用已有连接，其中还可能承载页面、音频、视频、广告和控制请求。

如果部署时拿不到准确 `t0`，应使用：

```text
较长观测区间
→ 多个重叠滑动窗口
→ 每个窗口编码为 embedding
→ Attention / Multiple Instance Learning 聚合
```

训练时也必须加入起点偏移，例如 `-5、0、+5、+10 秒`，不能训练时使用完美起点、测试时从任意位置开始。

## 多连接融合

同一次播放可能涉及多个 QUIC 连接或五元组路径。可采用两种组织方式：

1. 将所有候选事件按全局时间排序，并为每个事件增加匿名 `path_id`。
2. 每条路径使用共享编码器，再通过 permutation-invariant Set Attention 融合。

不能把固定的“第 1 条连接”解释成视频连接，也不能使用真实路径身份作为类别特征。

## 不应作为主输入的字段

- IP、MAC、真实五元组和端口。
- CID 原始字节、UDP 校验和、QUIC 密文。
- TTL、IPv6 Flow Label 和其他路径/设备标识。
- 文件名、目录、绝对时间和采集顺序。
- CDN 地址或可以直接映射采集批次的字段。

QUIC 版本、长/短头和 CID 长度建议只作为消融项，因为它们可能更多反映客户端版本、采集日期或服务部署，而不是视频内容。

## 推荐实现顺序

```text
第一阶段：最小事件序列
[signed UDP payload, global IAT]

第二阶段：完整事件序列
[signed UDP payload, global IAT, path IAT, relative time] + path_id

第三阶段：20/100/500 ms 多尺度时间 Bin

第四阶段：事件序列与多尺度 Bin 双视图融合
```

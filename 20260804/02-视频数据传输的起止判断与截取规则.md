# 视频数据传输的起止判断与截取规则

在 QUIC 加密流量中，无法直接看到 HTTP/3 请求和响应内容，必须通过旁路可观察特征判断视频数据何时开始、何时结束。本文基于实际 PCAP 数据验证多种判断方法，并给出可操作的截取规则。

## 1. 测试数据概况

| 属性 | 值 |
| --- | --- |
| 总包数 | 77,212 |
| 总时长 | 335.6 秒 |
| QUIC 1-RTT 包（服务器→客户端） | 73,760 |
| 其中大包 ≥ 1200B | 73,203 (99.2%) |
| 其中中包 200-1199B | 169 (0.2%) |
| 其中小包 < 200B | 388 (0.5%) |
| 30 条五元组路径 | 主路径占 97% 流量 |

## 2. 视频数据开始传输的判断

没有单一明确标志，但有多层信号可组合判断。

### 2.1 方法 1：DNS 域名信号（最可靠的前置信号）

```text
redirector.googlevideo.com  → 视频重定向服务器
*.googlevideo.com           → 视频内容分发网络（CDN）节点
```

一旦看到 DNS 查询 `redirector.googlevideo.com` 或 `rr*---sn-*.googlevideo.com`，后续一定会有视频数据传输。实测 DNS 查询与对应 IP：

| 时间 | DNS 查询 | 对应 IP | 用途 |
| --- | --- | --- | --- |
| 1.67s | redirector.googlevideo.com | 142.250.199.78 | 视频重定向 |
| 1.84s | rr1---sn-i3belnsy.googlevideo.com | 74.125.171.230 | 视频 CDN #1 |
| 1.84s | rr1---sn-i3b7knlk.googlevideo.com | 173.194.4.230 | 视频 CDN #2 |
| 1.88s | rr3---sn-oji3b5-58.googlevideo.com | 173.194.51.51 | 视频 CDN #3 |
| 10.97s | rr3---sn-i3b7kn6k.googlevideo.com | 209.85.229.136 | **主视频 CDN** |

### 2.2 方法 2：QUIC 连接目的地分类

将所有服务器 IP 按 DNS 域名归类：

| 类别 | 域名模式 | 代表 IP | 传输量 | 判断 |
| --- | --- | --- | --- | --- |
| **视频 CDN** | `*.googlevideo.com` | 209.85.229.136 等 | 92 MB (97%) | 视频数据 |
| API 服务器 | youtubei.googleapis.com | 216.239.38.223 | 58 KB | 元数据/控制 |
| 缩略图 | i.ytimg.com | 142.250.197.118 | 1.1 MB | 图片 |
| 头像 | yt3.ggpht.com | 142.250.198.33 | 148 KB | 图片 |
| 搜索建议 | suggestqueries.google.com | 142.250.197.110 | 12 KB | 文本 |
| 统计 | s.youtube.com | 173.194.174.100 | 11 KB | 播放统计 |

**规则**：目标 IP 属于 `*.googlevideo.com` 的 QUIC 连接 = 视频数据连接。

### 2.3 方法 3：吞吐量突变检测

秒级 IO 统计呈现清晰的"静→动"分界：

```text
第 0 秒：123 KB  (DNS + 握手)
第 1 秒： 66 KB  (握手 + 少量数据)
第 2-4 秒：~0 KB   (空闲，客户端解析中)
第 5 秒：192 KB  ← 突然上升，首个视频段
第 11 秒：2.3 MB  ← 爆发，主视频流开始
```

**规则**：当秒级吞吐量从接近 0 突增到 > 100 KB/s，且持续包来自 `googlevideo.com` IP，判定视频数据开始。

### 2.4 方法 4：包大小双峰分布

```text
服务器→客户端 QUIC 1-RTT 包大小分布：
  大包 (≥ 1200B)：73,203 个 (99.2%)  ← 几乎全是视频数据
  中包 (200-1199B)：   169 个 ( 0.2%)  ← 过渡/尾部
  小包 (< 200B)：      388 个 ( 0.5%)  ← ACK/控制帧
```

**规则**：连续出现 ≥ 5 个大包（≥ 1200B）从同一服务器 IP，判定该连接正在传视频数据。

## 3. 视频数据结束传输的判断

### 3.1 方法 1：突发间隔法（最实用）

视频数据以 DASH 分段模式"一坨一坨"传输，每段之间有明显间隔。实测主视频 CDN (209.85.229.136) 的突发段分析（idle_threshold = 0.5s）：

```text
VideoSeg#00: t=  11.06s  dur=0.670s  size=0.94 MB  rate=1476 KB/s  ← 初始缓冲(码率探测)
VideoSeg#01: t=  19.20s  dur=0.217s  size=2.80 MB  rate=13527 KB/s
VideoSeg#02: t=  29.51s  dur=0.132s  size=2.56 MB  rate=20261 KB/s
...
VideoSeg#34: t=326.06s  dur=0.507s  size=2.51 MB  rate=5179 KB/s  ← 最后一段
```

**规则**：连续 5 秒没有从 `googlevideo.com` IP 收到 ≥ 1200B 的 QUIC 包，判定视频传输结束。

### 3.2 方法 2：QUIC 连接关闭帧

QUIC 有显式 `CONNECTION_CLOSE` 帧，但实测中 YouTube 倾向于让连接保持空闲而非主动关闭。因此不能依赖连接关闭帧作为结束标志。

### 3.3 实测判定结果

```text
最后一段视频数据：326.06s (Seg#34)
最后的包：        335.58s (MDNS 包，无关)
差距：           ~9.5 秒无视频数据

视频传输区间：11.06s ~ 326.57s (约 315 秒 ≈ 5 分 15 秒)
```

## 4. 视频传输段的指纹特征

对流量指纹研究最关键的观察：

### 4.1 突发模式（Burst Pattern）

视频数据不是匀速的，而是"一坨一坨"地来——11 秒爆发 2.3 MB/s，然后安静几秒，19 秒再爆发。这就是 DASH 自适应码率的分段下载模式。

### 4.2 包大小双峰分布

视频数据包几乎都是 1292 字节（QUIC over UDP 的最大载荷），而控制包只有 66-77 字节。这种双峰分布是 QUIC 视频流的典型指纹。

### 4.3 多 CDN 节点并行

同一视频从多个 `googlevideo.com` 节点下载数据，YouTube 根据网络状况动态切换 CDN 节点。实测主 CDN (209.85.229.136) 占 97% 流量，但早期也有从 216.239.38.223 和 142.250.197.118 下载数据的段。

### 4.4 分段大小模式

稳定状态下，每个突发段的大小约为 1.5-3.0 MB，传输速率约 5 MB/s。这些数值与视频编码码率（av01 1080p@24fps）直接相关。

## 5. 视频段自动检测的伪代码

```python
VIDEO_CDN_DOMAINS = ["*.googlevideo.com"]
LARGE_PACKET_THRESHOLD = 1200  # 字节
VIDEO_END_TIMEOUT = 5.0        # 秒

# Step 1: 从 DNS 响应构建 video_cdn_ips 集合
for dns_response in pcap.dns_responses:
    if dns_response.domain matches VIDEO_CDN_DOMAINS:
        video_cdn_ips.update(dns_response.answer_ips)

# Step 2: 找到首个视频 CDN 大包突发
# 规则：连续 ≥ 5 个 ≥ 1200B 的包来自 video_cdn_ips
first_video_time = None
consecutive_large = 0
for d in datagrams:
    if d.src_ip in video_cdn_ips and d.udp_payload_length >= LARGE_PACKET_THRESHOLD:
        consecutive_large += 1
        if consecutive_large >= 5:
            first_video_time = d.timestamp - (consecutive_large - 1) * avg_iat
            break
    else:
        consecutive_large = 0

# Step 3: 找到视频数据结束
# 规则：从 video_cdn_ips 连续 5 秒无 ≥ 1200B 的包
last_video_time = find_last_large_packet_time(video_cdn_ips)

video_interval = (first_video_time, last_video_time)
```

## 6. 特殊注意事项

| 陷阱 | 说明 |
| --- | --- |
| i.ytimg.com 也会传大包 | 缩略图下载也会产生约 1 MB 的大包突发，但域名不是 googlevideo，用 DNS 映射可以区分 |
| 早期码率探测段很小 | 首段可能只有 0.94 MB，这是 YouTube 在做 ABR 码率探测，不要误判为非视频数据 |
| youtubei.googleapis.com 偶尔传大包 | API 连接的初始页面数据+视频 manifest 也可能产生 2-3 MB 突发，但不是视频切片本身 |
| 多 CDN 并行 | 同一视频从多个 googlevideo 节点下载，需按五元组分连接追踪 |
